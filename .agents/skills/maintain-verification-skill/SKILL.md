# Maintain a Verification Skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `create-verification-skill` (or any project-local verification skill with a feature map under `.agents/skills/verify-*/`). The unit of rigor is the **feature**, not every sentence: cover every feature file from source and exercise every feature live.

## Outcomes

Pick one and state it explicitly at the end of the run:

- **clean** — every feature got source and live coverage; nothing worth shipping. No branch, no PR.
- **changed** — one PR ships proven doc, harness, or feature-map corrections.
- **blocked** — coverage could not finish or a proven fix could not ship safely. State the exact blocker.

## Edit Scope

Only edit the verification skill's own directory (`.agents/skills/verify-<app>/`: its `SKILL.md`, `features/`, and any harness scripts it owns). **Never edit product code during a maintenance run:** a behavior the map describes that the app no longer does is either **doc drift** (fix the map) or a **product regression** (report it to the user; do not paper over it in docs).

## Pass

0. **Locate the target.** Find the verification skill to maintain: the project-local skill under `.agents/skills/verify-*/` whose body has `Launch`/`Drive` sections and a `features/` map. Several candidates → ask which one; none → stop and point at `create-verification-skill` instead of inventing a target.

1. **Index hygiene.** Read `features/README.md` and list its sibling `.md` files. Fix missing, extra, duplicate, or dead links. Keep it lightweight; no generated inventory bloat.

2. **Source wave.** Launch one read-only `research` subagent per feature file concurrently. Each subagent explains "how does this user-facing feature work today?" from source (`src/api/`, `src/vehicles/`, `src/config_yaml.rs`, `web/src/App.tsx`, `web/src/pages/`, `web/src/components/`), flags likely doc drift with concrete file/line citations, and returns one concise live-verification recipe. Subagents never drive the app and never edit files. Return shape per feature:
   - feature summary
   - source entry points
   - likely drift (with citations) or `none`
   - one concise live recipe

3. **Reconcile.** Confirm every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; do not re-prove clean claims. Sweep recent git churn (`git log` over `src/api/`, `web/src/App.tsx`, `web/src/pages/`) for user-facing routes or behaviors missing from the map — require a concrete source path before calling one missing.

4. **Live pass.** Required even when source looks clean. The coordinator owns all driving; follow the verification skill's own `Launch` model (for `tesla-apiscraper-rs`, typically one isolated Rust server + mock Tesla API + seeded InfluxDB 1.8 test database driven serially). Exercise every mapped feature at least once, holding three invariants throughout, whatever fails:
   1. **Health-checked before driving:** Run `doctor` before the first drive, on each fresh session, and again after any failed drive. Where `doctor` cannot see a failure (e.g., wedged SPA state on a healthy server), reset to a known state or relaunch rather than hoping.
   2. **Evidence survives cleanup:** Confirm captured proof artifacts still exist at their named path after every cleanup; never assume.
   3. **Zero leaked residue:** Nothing a drive started outlives that drive's usefulness — clean up failed-iteration processes, temp `CONFIG_DIR`s, and temporary InfluxDB test databases whether the session exited normally or got stuck.

   Handling special cases during the live pass:
   - A `doctor` failure caused by skill drift is drift: fix it under edit scope and retry once (restarting only what the fix invalidated) before calling the pass `blocked`.
   - Mark a feature `verified-unreachable` only with the concrete unmet prerequisite (e.g., missing InfluxDB service, auth, OS/external state) and the exact route/command attempted; if the map omits that prerequisite, that is doc drift.
   - Any harness fix made during triage must be **re-driven live** before shipping.
   - Final teardown runs after the last drive (including re-proofs), leaving zero stray processes/DBs while preserving proof artifacts.

5. **Triage.**
   - Wrong or missing user-POV description → **doc drift** → fix in the skill/map.
   - Working app behavior the harness cannot drive → **harness gap** → fix under edit scope (keeping helper scripts executable and documented in `SKILL.md`), then re-prove live.
   - App behavior that is actually broken → **product gap** → record with reproduction evidence for the user; keep product fixes out of this maintenance PR.

6. **Ship or stop.**
   - For **changed**: re-read every modified file in `.agents/skills/verify-<app>/`, commit cleanly on a feature branch, and open at most one PR of proven corrections.
   - For **clean** or **blocked**: no PR; report the outcome, feature coverage, any product gaps, and any blockers honestly.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location; do not commit them.
